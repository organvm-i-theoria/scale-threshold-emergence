PRIMITIVE CANON v1


Controlled Conceptual Vocabulary for the Framework


The Primitive Canon defines the minimal vocabulary allowed to appear in mechanism models, module specifications, threshold packages, and simulation architecture.


A primitive is not a theory.
It is a minimal conceptual unit required to describe organized reality.


The canon prevents uncontrolled conceptual drift across research lanes.



I. Canon Design Principles


The primitive system obeys five rules.


Rule 1 — Minimality


Primitives must be irreducible within the framework.


If a concept can be expressed as a combination of other primitives, it should not be a primitive.



Rule 2 — Cross-Domain Validity


A primitive must be usable across multiple domains:


physics
chemistry
biology
cognition
society
symbolic systems



Rule 3 — Non-Redundancy


No two primitives should encode the same conceptual function.



Rule 4 — Operational Meaning


Every primitive must correspond to something that can appear in:


mechanism description
system model
simulation architecture



Rule 5 — Stability


Primitive definitions should change only rarely and only through formal revision.

XIII. The Three Biggest Failure Modes


Projects attempting to build universal frameworks almost always fail for the same structural reasons.



Failure Mode 1 — Ontological Explosion


The system accumulates hundreds of poorly defined concepts.


Symptoms:


vocabulary keeps expanding
definitions drift
concepts overlap
framework becomes incoherent


Cause:


No primitive governance.


Solution:


strict primitive canon
controlled vocabulary
concept change review


This is why the Primitive Canon is essential.



Failure Mode 2 — Premature Law Freezing


A model becomes canon before enough research exists.


Symptoms:


simulation rules become dogma
architecture hardcodes assumptions
alternative theories become difficult to test


Cause:


Software architecture locked too early.


Solution:


law profiles instead of fixed laws
mechanism packs instead of single implementations
parameterized models


Your instinct about avoiding premature laws is exactly right.



Failure Mode 3 — Research Entropy


The research program becomes unmanageable.


Symptoms:


hundreds of sources
notes scattered across folders
connections between ideas lost


Cause:


lack of:


knowledge graph
structured notes
mechanism registry
threshold tracking


Solution:


structured research lanes
knowledge graph
reading tracker
mechanism extraction



XIV. The Success Condition


Projects like this succeed only when three systems remain balanced.


conceptual framework
research program
software architecture


If any one grows faster than the others, the system collapses.


The correct dynamic is:


research informs architecture
architecture tests research
framework integrates both
